# 提交信息规范

拟写提交信息前，先用 `git diff --cached` 核对暂存区，以本次提交的实际改动为准。如果暂存区为空，可以根据用户指定的改动拟写草案，暂存后再核对。

## 标题

采用 [Conventional Commits](https://www.conventionalcommits.org/zh-hans/v1.0.0/)。标题格式为 `type(scope): 中文摘要`，省略范围时写作 `type: 中文摘要`。类型和范围用小写英文，半角冒号后留一个空格。摘要用动词开头，一行说清具体变化。

| 类型 | 主要用途 |
| --- | --- |
| `feat` | 增加功能 |
| `fix` | 修复缺陷 |
| `build` | 调整构建配置或依赖 |
| `docs` | 更新文档 |
| `refactor` | 在保持现有行为的前提下调整代码结构 |
| `test` | 新增或调整测试 |

按提交的主要目的选择类型。例如，修复拖拽缺陷并附带回归测试时用 `fix`。范围选择便于检索的功能区或工具名，例如 `workspace`、`allapps`、`quickstep`、`gradle`、`codex`。跨模块且没有明确主范围时可省略。

示例：

```text
docs(codex): 添加 Launcher3 项目指引和构建排查笔记
fix(workspace): 修复跨屏拖拽后图标回到原位置的问题
```

## 正文与验证

简单改动只写标题。修复原因不直观或行为因构建目标而异时，在标题后空一行，用正文说明触发条件、原因及适用目标。例如，构建问题可以写明受影响的 Gradle 变体或 Soong 模块。

需要记录验证时，在末尾另起一段，用 `Test: <实际执行的命令或设备操作及结果>`。只填写本次实际完成的验证。
